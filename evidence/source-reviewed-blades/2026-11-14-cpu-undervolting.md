## Exact Device.dll evidence

All RVAs below refer to Device.dll 2.12.0.2723 (above). Starting from an independently admitted, already-running driver known to service Control, use bounded typed operations only. These are directly source-reviewed commands. No real Razer 0508 hardware was exercised.

- Hardware identity: CPhoenixCPU::Init locates 1022:14E8 at 4F2C2; normal PCI config DWORD at 00:00.0 is 14E81022. [PCI IDs 82dfd7fd](https://github.com/pciutils/pciids/blob/82dfd7fd84c9033ac3db474c65335ddb2dab972a/pci.ids) names 14F0 and 14F1 as Phoenix Data Fabric functions 0 and 1, validate 00:18.0 and 00:18.1 config dwords 14F01022 and 14F11022. No Strix IDs are inherited.
- PCI enumeration: AC910 zeroes the 28-byte header; IOCTL 0x81112F18 at AC9D4 takes/returns 28 bytes, count at offset 24. Second AC A99 takes/returns precisely 28 + 52*count, count in header; each record has DWORD bus/device/function at offsets 0/4/8 and DWORD native PCI ID at +12 (low ushort vendor). The SDK's own STL map converts IDs to vendor-high internally at ACB17–ACB2F. Cap count, reject wrap, bad lengths, duplicate addresses and malformed replies.
- PCI read: AC660–AC79A uses 0x81112F24, 20-byte DWORD tuple bus, device, function, offset, width; output has same 20-byte header plus width payload; exact returned byte count must equal width+20; SDK additionally checks returned width >0 before copying. Direct readback at ADE4B–ADEB6 uses offset C8 and width 4, reads dword +20. Hardening can require full unchanged header, exact width 4.
- SMN: ADCA0 et seq uses 0x81112FF8, 12 bytes (selector/data ID resolved for PCI C4/C8, uint32 value, root bus), zero result bytes. SDK reads back through C8. RSMU command 03B10A20, response 03B10A80, arguments 03B10A88 and 03B10A8C. Successful driver submission is distinct from firmware response.
- V22 driver dispatch independently checks 0x81112F18, 0x81112F24, 0x81112FF8, 0x81112F08 at RVAs 1C4D–1CA3. No new arbitrary PCI/SMN operation is offered.
- Core orientation: GetCurrentCoreOrientation 4F080–4F0FC demands CCD 0 and PCI bus 0, device 0x18, function 1, offset 0x140, width 4. Native getter uses eight slots. Mask low 8. Core fuse path 50320–503BB reads SMN 0x5D528, inverts disabled bits [14:7] to produce enabled mask. Require 0xFF in both, real eight physical cores / 16 threads. Exact product independently selects the Phoenix/Hawk family implementation.
- RSMU 0x82 capability: 4F3C5–4F495 uses zero input words, one output word. Bit 2 populates the exact gate at global DC771 checked at getter 5375D and setter 5362F. Preserve any separately required conditions for other backends.
- Multi-core live baseline: CPhoenixCPU::GetCurveOptimizerStatus RVA 53750–53930. Obtain enabled D18F1 mask, iterate raw core ordinal 0..7, send 0xE1 with input ordinal (no shift), read actual low signed 16-bit result per core and stop at first failure. It independently derives zero/all-equal/mixed status from these observations. Per-core mutation 53620–53748 requires capability, CCD=0, ordinal<=7 and a fresh range check, then packs (core << 20) | uint16(value), opcode 0x53; all-core 53520–53610 is a distinct 0x5D signed int32 call. Voltage-only setter contains no PPT mutation or fused PPT limit gate. Use the existing one-core-at-a-time journal/verification implementation where supported; restore the exact original core vector.
- Metadata: 47C0 reads root/wmi AMD_ACPI.QueryVersion Version with returned VARIANT VT_I4 and selects interface versions 3 through 7 (4893–48B4). Fresh live-range native route: C6A0 selector 5000A dispatch via DEB0 entry 8 to D96A→C620. 5B60–5EA3 calls AMD_ACPI.GetMinMaxSteppingValues with id VT_I4 then extracts output pack and fields Min, Max, Stepping from its embedded WMI object; signedness for individual outputs below DWORD precision is not asserted. C620 compares nonnegative **magnitude** of requested CO steps against min/max and checks (magnitude-Min)%Stepping==0. Native setter does not use GetDValues, does not require Current or Value and does not assume min 0/max 50. Use the narrower negative user-visible CO bounds and ensure each requested nonzero magnitude/restoration is admissible against a complete freshly decoded actual range; running current still comes solely from per-core E1. Zero should be admitted only as permitted by the actual setting range.
- PM peer table: 4F78B–4F836 requests two result words from 0x66 and combines them as a physical address; 0x06 at 4F8CD queries PM version; 4E9E2 uses 0x65 with argument 3 to refresh. AC2A0–AC3B5 copies via 0x81112F08 input 4 (length only), output 4+length checked, copied bytes at +4, no arbitrary physical address in the wire request. 4EA15 switch table 4EEA4 has only 4C0003:B18, 4C0004:B1C, 4C0005:AF8, 4C0006:AFC, 4C0007:B00 and 4C0008:AF0. Cap new support to the reviewed layouts actually implemented. A narrow first admission may require 4C0008 and AF0; obtain this fresh on any 0508. A non-Razer 8945HS was [independently observed](https://www.cnx-software.com/2024/06/11/geekom-a8-review-ubuntu-24-04-linux-amd-ryzen-8945hs-mini-pc/) at 4C0008; that is not a Blade physical result. [RyzenAdj pinned api.c](https://github.com/FlyGoat/RyzenAdj/blob/5775fc3e6dbb25c7030ee2d100a1bdd6e8bf2d0a/lib/api.c) confirms 4C0008/AF0 and byte offsets for IEEE754 watts STAPM 0, fast PPT 8, slow PPT 16. Require finite, valid and equal independent before/after values for apply/restore. 4C0009 is recognized by RyzenAdj but it is outside the pinned AMD DLL's PM table switch. Exact Razer firmware PM layout in use remains unobserved.
